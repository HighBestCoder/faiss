## 1. 本轮新增优化 O17

**问题**: HNSW search 热路径 (`HNSW.cpp:461`) 调用 `qdis.distances_batch_8(...)`，
但 SQ 系列的 `DCTemplate<Q, Sim, AVX512/AVX2>` **没有 override** 这个方法，
落到 `DistanceComputer::distances_batch_8` 默认实现 → 拆成 8 次串行 `operator()` 调用，
每次只有 1 条 FMA 依赖链，Ice Lake 上 ~5 周期延迟完全暴露，IPC ≈ 0.2。
这正是"AVX2 vs AVX-512 在该工作负载上差距很小"的根因。

**解决**: 在 `sq-avx2.cpp` 和 `sq-avx512.cpp` 的 `DCTemplate` 特化里
override `distances_batch_4 / distances_batch_8`，
单循环 + N 个独立累加器，FMA 流水填满。

**Sanity (cohere_medium_1m, HNSW32,SQfp16, efC=200, efS=64)**:

| 版本 | QPS_1T | QPS_16T | R@10 |
|---|---|---|---|
| v1.14.1 + 之前所有 opts (phase3 ref) | 1,304 | 11,799 | 96.36% |
| **+ O17 (本轮)** | **2,063** | **27,842** | 97.01% |
| **提升** | **+58.2%** | **+136.0%** | 持平 |

Commit: `228bc0953` "O17: SQ DistanceComputer parallel distances_batch_4/8 (AVX2/AVX512)"

## 5. 关键结论

1. **SQ8 把 30M RSS 从 61 GB 降到 38.1 GB（-36% / -22 GB）**。
2. **R@10 几乎无损**（efS=256 时 95.06%，仅比 SQfp16 低 0.89 pt），efS=512 可达 96.45%。
3. **R@100 几乎无损**（-0.19 pt @ efS=256）。
4. **QPS 反而更高**（+15~30%）：cache 占用减半 + O17 流水优化。
5. **build time 也更短**（-13.6%）。
6. **R@10 ≥ 95% 的甜点**：HNSW48,SQ8 efC=512 efS=256 → 163 / 2046 QPS, 38.1 GB RSS。

> 这意味着 30M 上 **SQ8 是无脑替代 SQfp16 的选择**：内存少 36%、QPS 高 15~30%、recall 仅降 ~1 pt。
> 直接将 30M 的默认推荐从 HNSW48,SQfp16 改为 **HNSW48,SQ8**。

### 与 P1-1 (M=48,SQ8) 和 SQfp16 baseline 三方对比

| 配置 | RSS | Build | efS | R@10 | R@100 | QPS_1T | QPS_16T |
|---|---|---|---|---|---|---|---|
| HNSW48,SQfp16 baseline | 61.0 GB | 7.0h | 256 | 95.95% | 90.11% | 137 | 1,769 |
| HNSW48,SQ8 (P1-1) | 38.1 GB | 6.0h | 256 | 95.06% | 89.92% | 163 | 2,046 |

### 关键观察

1. **RSS 再省 3.6 GB**：38.1 → 34.5 GB（达到了 plan 的"期望" ≤ 35 GB 门槛 ✅）。
2. **R@10 ≥ 95% 的甜点变化**：M=32 需要 efS=512 才达 95.39%，而 M=48 在 efS=256 就 95.06%。
3. **M=32 efS=512 vs M=48 efS=256 直接对比**：
   - QPS_1T: 116 vs 163（M=32 慢 29%）
   - R@10: 95.39% vs 95.06%（M=32 略高 0.33 pt）
   - R@100: **92.33% vs 89.92%（M=32 高 2.41 pt）** ← R@100 反超
   - RSS: 34.5 GB vs 38.1 GB（M=32 省 3.6 GB）
4. **M=32 efS=256 是最高 QPS 候选**：QPS_16T 2,961，比 P1-1 efS=256 的 2,046 高 +45%；但 R@10 只有 93.38%，仅适合宽松 recall 场景。
5. **构建时间也线性下降**：M=48→32 build 6.0h→5.1h（-15%）。
6. **R@100 ≥ 95% 仍未达成**：所有 SQ8 配置 R@100 最高 94.30%（P1-1 efS=512），下一阶段需要看 efS 进一步增大或 rerank。

## D3 部分 — VNNI int8 IP 优化（recall 不达预期，未上车）

日期: 2026-05-07
配置: `HNSW48,SQ8` efConstruction=512 efSearch={512, 1024}
代码改动: `faiss/impl/scalar_quantizer/sq-avx512.cpp` 新增 `DCTemplate<QT_8bit, NON_UNIFORM, IP, AVX512>` 偏特化（~290 行）
Log: `llm/results/30m-mem/v1-18_M48_efC512_SQ8_vnni.log`

### 改造原理

数学（NON_UNIFORM SQ8, IP）：
```
y_recon[i] = (c[i] + 0.5) / 255 * vdiff[i] + vmin[i]
<x, y> = sum_i (x[i] * vdiff[i] / 255) * c[i]  +  sum_i x[i] * (0.5*vdiff[i]/255 + vmin[i])
       = sum_i w[i] * c[i]                     +  bias
```

`set_query` 一次性算 `w[i]`、`bias`、`max|w|`，把 `w[i]` 量化为 s8 (`q8[d]`)。
内层循环用 `vpdpbusd(acc, c_y_u8, q_int8_s8)`（u8×s8→i32 一指令做 4 MACs），
取代原 `cvtepu8_epi32 + cvtepi32_ps + scale_fmadd + dot_fmadd`。
返回 `s_q * dot + bias`，ranking 数学等价。

### 根因分析

1. **HNSW navigation 比 ranking 敏感**：query s8 量化噪声不只重排前 k，还让中间步骤选错邻居，路径偏移在跨层 greedy 中累积，最终 recall 损失被放大。在 1M 上仅 -1 pt，到 30M 放大到 -3.6~3.85 pt。
2. **scale_q 的 dynamic range 问题**：`max|w|` 是单 query 全局 scale，d=768 中只要少量大值（query L2-normalized 后通常服从尖峰分布）就会拉宽 scale，多数维度的 q8 实际只剩 2~3 bit 精度。
3. d=768 + s8 累加上限 ~ 768 × 255 × 127 ≈ 2.5e7 << INT32_MAX，未发生 i32 溢出，可排除算术问题。

## 附录 B：SQ8 训练机制 — FAISS 我们的实测做法 vs Qdrant

### B.1 我们 30M 实验里 SQ8 实际怎么 train 的

代码：`llm/bench_task.cpp:269-287`

```cpp
if (!idx->is_trained) {
    int train_n = std::min(nb, 1000000);   // 前 1M 条
    // 顺序读 base.fvecs 前 train_n 条
    l2_normalize(train_data.data(), train_n, d);
    idx->train(train_n, train_data.data());
}
fvecs_stream_add(base_path.c_str(), idx);  // 全 30M 分 100K/批 add
```

**关键事实**：

| 项 | 值 |
|---|---|
| 训练样本量 | base.fvecs **前 1,000,000 条**（顺序，非随机） |
| 占总数据比例 | 1M / 30M = **3.33%** |
| 训练算法 | `train_NonUniform` + `RS_minmax`（FAISS 默认） |
| 输出 | 每维独立 `vmin[j], vdiff[j]`，共 768×2 = 1536 个 float |
| 训练耗时 | < 5 秒（单次扫描 1M×768） |
| 训练时机 | `idx->add` 之前显式调用一次，之后 30M add 全部复用同一份参数 |

**给非工程同事的一句话**：SQ8 训练就是用前 100 万条向量，每个维度独立算一遍 min/max（共 1536 个浮点数），花几秒钟，之后 3000 万向量编码全用这套参数。

### B.2 Qdrant SQ8 的做法（源码 `lib/quantization/src/encoded_vectors_u8.rs`、`quantile.rs`）

| 项 | Qdrant |
|---|---|
| 缩放粒度 | **全局一对** `(alpha, offset)` = `(max-min)/127, min` 标量 |
| 等价于 FAISS 的 | `QT_8bit_uniform`（不是 `QT_8bit`） |
| 训练数据 | 默认扫**全段**取 min/max；带 `quantile` 时随机抽 5000 条 |
| 训练接口 | **无显式 train**；segment build 时 `EncodedVectorsU8::encode` 内部 two-pass 自动算 |
| 训练时机 | 每个 segment 独立训一次，**segment 间不共享** |
| 用户可调参数 | 仅 `quantile`（0.5~1.0），样本量 `SAMPLE_SIZE=5000` 是硬编码 |

### B.3 核心差异表

|  | FAISS（我们用的 SQ8） | Qdrant SQ8 |
|---|---|---|
| 缩放 | per-dim（768 对） | global（1 对） |
| 训练样本 | 前 1M（3.3%，顺序） | 全段 / 5000 随机 |
| Outlier 处理 | 无 | 可选 quantile trim |
| 训练接口 | 显式 `train()` | 隐式（segment build） |
| 重训粒度 | 一次全局 | 每 segment |
| 适合场景 | 一次性大批量构建 | 增量上传 + 后台 optimize |

### B.4 你的疑问：为什么 Qdrant 不在第一次 upsert 时增量维护 (min, max)？

这是个非常合理的工程问题——理论上 min/max 完全可以 streaming 维护：每条 upsert 进来比较一次，O(d) 即可，optimize 时直接拿来用，省一遍扫描。

阅读 Qdrant 源码（`segment_builder.rs`、`quantized_vectors.rs:1316-1434`）后能看到，这个设计选择是**有意的**，原因可能在以下几点：

**1. Segment 是 immutable 的，optimize 是 build-from-scratch**
Qdrant 的 segment 模型：写入先进 in-memory "appendable" segment（无量化），后台 optimizer 把多个小 segment merge 成大的 immutable segment 时**才**做 quantization。merge 输入可能来自多个 source segment、加上 deletion mask、加上 payload filter，所以"参与本次 build 的向量集合"在 optimize 启动那一刻才确定。即使 upsert 时维护了 (min, max)，optimize 时也要按"实际参与 merge 的子集"重算，否则 deletion 后的 min/max 就是错的（被删的极值还在）。

**2. Quantile trim 不可增量**
如果用户开了 `quantile=0.99`（推荐做法，抗 outlier），需要的是 0.5%/99.5% 分位数，不是 min/max。分位数本质上要"看完所有数据再排序"才能算（或者用 P² 这种近似算法，Qdrant 有但只用在 binary path）。增量维护一个能"删点也能加点"的精确分位数结构成本远高于 build 时一遍扫描，工程上不划算。

**3. Per-segment 局部最优 vs 全局统一**
每个 segment 独立算 (alpha, offset) 的好处是：不同 segment 的数据分布不一样（按时间/topic 聚类），局部 codec 比全局更紧。如果 streaming 维护一份全局 (min, max)，会被早期 outlier 拉宽，后续 segment 编码精度反而下降。这是 Qdrant 选择"每 segment 独立训"的核心动机，而每 segment 独立训就意味着不能复用全局的 streaming 统计。

**4. Append 路径要求极简**
Qdrant 的写入 SLA 是低延迟（毫秒级），upsert 路径里加任何"为后续 optimize 维护元数据"的工作都会拖慢 hot path。把所有 expensive 工作堆到后台 optimizer，是典型 LSM-tree 思路（参考 RocksDB compaction）。多扫一遍 1~10M 向量在后台无所谓，但卡 upsert 的 P99 用户会立刻投诉。

**5. Code 复杂度 / 正确性**
Streaming min/max 看起来简单，但要正确处理：deletion、segment split、segment merge、crash recovery（统计要 fsync 否则重启丢失）、并发 upsert（多线程更新一份共享 min/max 要锁）。一遍扫描的 build-time 算法是确定性的、无状态的、好测的——工程上更安全。

**结论**：Qdrant 的设计是在 "upsert 路径轻 + segment 局部最优 + 支持 quantile trim" 三个目标下的合理 trade-off，宁愿后台多花一遍 I/O。我们 FAISS 这边因为是离线 batch 构建（一次 build 不重来），用 1M 子集一把训完是更合适的方案——两边不是谁优谁劣，是场景不同。
